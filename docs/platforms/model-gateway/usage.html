Model Gateway Usage

Use these steps to work with the gateway after installation. Code snippets are ready to copy and adjust.

Make a request​

  • curl
  • Node
  • Python
curl -X POST https://gateway.example.com/v1/chat \
  -H "Authorization: Bearer $GATEWAY_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"route":"chat-primary","messages":[{"role":"user","content":"Summarize routing policy."}]}'
const res = await fetch('https://gateway.example.com/v1/chat', {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${process.env.GATEWAY_TOKEN}`,
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({
    route: 'chat-primary',
    messages: [{role: 'user', content: 'Summarize routing policy.'}],
  }),
});
const data = await res.json();
console.log(data.route_used, data.trace_id, data.choices?.[0]?.message?.content);
import os
import requests

resp = requests.post(
    "https://gateway.example.com/v1/chat",
    headers={
        "Authorization": f"Bearer {os.environ['GATEWAY_TOKEN']}",
        "Content-Type": "application/json",
    },
    json={
        "route": "chat-primary",
        "messages": [{"role": "user", "content": "Summarize routing policy."}],
    },
    timeout=15,
)
resp.raise_for_status()
data = resp.json()
print(data["route_used"], data["trace_id"], data["choices"][0]["message"]["content"])
Verification

Confirm trace_id is present and route_used matches the intended route. Use the trace ID to find logs in observability dashboards.

Manage tools​

  • Register tools with schemas; tools are allowed per policy.
  • Align tool naming with the Context routing architecture when emitting events.

Handle responses​

  • Expect trace_id in responses; use it to join logs described in the Runtime observability note.
  • When fallbacks occur, the route_used field shows which provider responded.

Common pitfalls​

  • Missing policies lead to rejected calls; confirm configuration.
  • Overly broad tools increase risk; scope tools to routes.
  • Forgetting budgets can cause noisy alerts; configure budgets early.

Troubleshooting​

  • 401 Unauthorized: rotate tokens and confirm the service principal is allowed on the route.
  • 403 Forbidden: route or tool blocked by policy; check the policy store and budgets.
  • 429 Too Many Requests: back off with jitter; raise limits only after verifying budgets.
  • 503 Service Unavailable: check provider health and fallbacks; retry with circuit breakers.

Verification checklist​

  • Call succeeds with expected route_used and trace_id.
  • Budget counters increment as expected for the service.
  • Observability shows spans for the gateway call and downstream actions.
  • Tools invoked match the allowlist; no unexpected tool calls appear in logs.

Rollback and contingencies​

  • If a new route misbehaves, set it to inactive and revert to the prior route version in config.
  • Disable problematic tools by removing them from the policy and redeploying.
  • Lower budgets temporarily to contain cost while investigating.

Sequence: chat call with fallback​

sequenceDiagram
    participant App as App
    participant Gateway as Model Gateway
    participant Primary as Provider A
    participant Fallback as Provider B

    App->>Gateway: POST /v1/chat (route: chat-primary)
    Gateway->>Primary: Call with tools + policies
    alt Provider A healthy
        Primary-->>Gateway: Response + usage
    else Provider A down
        Gateway->>Fallback: Call fallback route
        Fallback-->>Gateway: Response + usage
    end
    Gateway-->>App: Response with route_used and trace_id

Model Context Protocol Overview

Model Context Protocol (MCP) defines a standardized way for models to consume tools and context with predictable schemas and controls. This overview explains when to adopt MCP, how it aligns with Verse patterns, and the guardrails required for safe use.

Problem this addresses​

  • Ad hoc tool schemas increase integration cost and error rates.
  • Models may invoke tools without sufficient guardrails, risking unintended side effects.
  • Context delivery is inconsistent across platforms, leading to brittle prompts and reruns.

Core idea​

  • Define a shared contract for context, tools, and invocations so models can interact with systems predictably.
  • Keep schemas versioned and discoverable, with capability negotiation between client and server.

When to use MCP​

  • You need multiple models or agents to consume the same toolset with minimal rework.
  • You want platform-neutral contracts that work across providers or gateways.
  • You plan to enforce safety, budget, and auditing consistently (see Model Gateway overview).

When not to use it​

  • A single, tightly controlled runtime with static prompts and no tool calls may not benefit.
  • If tools are highly bespoke and unlikely to be reused, MCP overhead might not be justified.

Architecture​

  • Client: sends requests, advertises capabilities (tooling, context formats), and receives results.
  • Server: exposes tools, schemas, and context sources; enforces auth, rate limits, and safety.
  • Gateway: optional front door that handles routing, budgets, and safety (see Model Gateway configuration).
  • Observability: traces tool calls, context fetches, and errors; align with Runtime observability.

Flow (simplified)​

  1. Client discovers server capabilities and supported MCP version.
  2. Client sends a request with tool name, arguments, and context references.
  3. Server validates auth, schema, and budgets; invokes the tool.
  4. Server returns result with metadata, usage, and trace IDs.
  5. Metrics and logs are emitted for auditing and tuning.

Reference contract (example)​

{
  "version": "0.2.0",
  "capabilities": {
    "tools": [
      {
        "name": "fetch_customer_profile",
        "schema": {
          "type": "object",
          "properties": {
            "customer_id": {"type": "string"},
            "fields": {"type": "array", "items": {"type": "string"}}
          },
          "required": ["customer_id"]
        }
      }
    ],
    "context": [
      {
        "name": "docs-index",
        "schema": {
          "type": "object",
          "properties": {
            "query": {"type": "string"},
            "top_k": {"type": "integer", "default": 5}
          },
          "required": ["query"]
        }
      }
    ]
  }
}

Guardrails and policies​

  • Auth: Use per-client credentials and short-lived tokens.
  • Schema validation: Reject requests that do not match the published schema; return clear errors.
  • Safety: Enforce tool allowlists per route; block high-risk actions unless explicitly permitted.
  • Budgets: Apply per-client and per-tool rate limits; integrate with Model Gateway budgets for consistency.
  • Observability: Require trace_id and route/tool metadata in logs and responses.

Interop with Verse patterns​

  • Use MCP tool contracts within the gateway to keep tool invocation predictable (Model Gateway usage).
  • Combine with Context routing architecture to deliver only the context each tool needs.
  • Apply Resilient workflows to handle timeouts, retries, and compensations around MCP tool calls.

Verification checklist​

  • Capability discovery works and returns the expected schema set.
  • Requests with missing or invalid fields are rejected with clear errors.
  • Tool calls include trace_id, route, and usage metadata for audit.
  • Budgets and rate limits trigger alerts when exceeded.

Promotion path​

  • Prototype MCP contracts in a staging server and capture notes in Exploration.
  • Once stable, store schemas with the service repo and reference them from gateway configs.
  • Record major contract changes in an ADR using the ADR template.
